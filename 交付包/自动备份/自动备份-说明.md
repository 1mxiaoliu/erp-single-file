# 那"每月导出一次"能不能免了

## 为什么会有这句话

**Supabase 免费版不提供自动备份**——官方只给付费版（Pro，$25/月）下载备份。
数据在它那边本身不会丢（机房有多重副本），但你**拿不到历史副本**：误删、误改之后，回不到昨天。

手动导出就是替代品。所以真正要解决的问题是：**让某个程序每天替你留一份。**

能，而且不用花钱、不用任何电脑开机、不用注册新账号。

---

## 三种办法，按推荐顺序

| 办法 | 花钱 | 要开机吗 | 能回到 | 难度 |
|---|---|---|---|---|
| **① 云端自动留历史版本**（推荐） | 0 | 不用 | 最近 24 小时每一版 + 180 天内每天一版 | **跑一段 SQL，2 分钟** |
| ② GitHub 定时任务，每天拉一份 | 0 | 不用 | 180 天 | 注册 GitHub，国内网页很慢 |
| ③ 手动导出 | 0 | 不用 | 你记得导的那几次 | 0 |

**选 ①。** 它不需要任何第三方服务，Supabase 自己就能干，而且比 GitHub 那套恢复得更精细——
出错了能回到"一小时前"，而不是"昨天"。

---

## 办法 ①：Supabase 自动留历史版本（推荐）

### 原理

在数据库里装一个**触发器**：每次有设备保存数据，数据库自动把**改动之前的版本**抄一份进历史表。
网页代码一个字都不用改，你也不用做任何日常操作。

### 安装（2 分钟）

1. Supabase 控制台 → 左侧竖排图标第 3 个（`>_`）→ **SQL Editor** → **New query**
2. 打开本目录的 **`Supabase历史版本.sql`**，全选复制，粘进去
3. 点 **Run**，看到 `Success. No rows returned` 就装好了

> 重复跑也没事，不会影响现有数据。

### 先花 30 秒查一下：到底装了没有

很多人以为装了，其实没有。在 SQL Editor 里跑这一行：

```sql
select count(*) from public.erp_doc_history;
```

- 报错 `relation "public.erp_doc_history" does not exist` → **没装**，回到上面第 2 步
- 返回一个数字（0 也算）→ 已装，跳过安装，直接看下一节

> 装之前的历史版本不会补记，只从安装那一刻开始留。

### 装好之后你还要做什么

**什么都不用做。** 没有"每月备份一次"，也没有"每周检查一次"。

每次有设备保存数据，数据库在写入前自动把旧版本抄一份进历史表，保留策略也在同一次写入里顺手执行。哪怕你半年不打开这个页面，历史版本也一直在。

只有两种情况需要你动手：

1. **要恢复**（改坏了、误删了）→ 用 `恢复数据.sql`
2. **要一份存在 Supabase 之外的副本**（怕连项目一起误删）→ 见文末"办法 ②"

### 出事了怎么恢复

打开本目录的 **`恢复数据.sql`**，里面分三段，照着顺序来：

1. **看有哪些版本**——列出时间、版本号、数据大小。数据突然变小的那一行之前，通常就是正常的
2. **取值看一眼**——先看某天的数据对不对，不改任何东西
3. **正式恢复**——把时间填进去，`Run`，返回 `UPDATE 1` 就成功

然后所有设备重新打开网页，就是恢复后的数据（脚本会自动把版本号 +1，让其他设备知道该拉新数据，不会拿旧数据盖回去）。

### 会占多少空间

免费额度是 500 MB。一个进销存的账本 JSON 通常在几十 KB 到几百 KB。

保留策略（脚本里已经写好，自动执行）：

| 时间范围 | 保留多少 |
|---|---|
| 最近 24 小时 | **每次保存都留**（能精确回到出错的上一分钟） |
| 24 小时～180 天 | **每天留最后一版** |

按每天 150 KB 估算，180 天大约 **27 MB**。够用很多年。

随时可以看占用：

```sql
select count(*), pg_size_pretty(coalesce(sum(pg_column_size(doc)),0)::bigint)
  from public.erp_doc_history;
```

嫌大就把 `180 days` 改成 `30 days` 再跑一次。

### 注意

- 历史表**没有对网页开放**（前端那个 key 读不到它），只有你登录后台能看
- 它解决的是"**改坏了能回去**"，不是"**机房出事**"——后者 Supabase 自己负责
- 想要一份**存在别处**的副本（比如换服务商、或者连 Supabase 项目都误删了），才需要办法 ② 或 ③

## 办法 ②：GitHub 定时任务（异地副本，国内较慢）

如果还想要一份**不在 Supabase 里**的副本，用这个。原理是让 GitHub 每天凌晨来把整本账拉走，存进一个私有仓库。

⚠️ 国内访问 github.com 经常很慢甚至打不开。**先试 ①，这个当备选。**

### 五步

**1. 建私有仓库**

github.com → 右上角 `+` → **New repository** → 名字 `erp-backup` → 选 **Private** → 创建

**2. 建 workflow 文件**

仓库里点 **Add file** → **Create new file**，文件名那一栏直接输入完整路径：

```
.github/workflows/backup.yml
```

把本目录的 `backup.yml` 全文粘进去 → Commit。

> 只写 `backup.yml`（不带前面的目录）会放到根目录，定时任务**不会执行**。

**3. 填两个变量**

仓库 **Settings** → **Secrets and variables** → **Actions** → **New repository secret**：

| Name | Secret |
|---|---|
| `SUPA_URL` | `https://你的项目ID.supabase.co` |
| `SUPA_KEY` | `sb_publishable_...` 或 `eyJ...` |

**4. 手动跑一次**

**Actions** 标签 → 左侧 `ERP 每日备份` → 右侧 **Run workflow**。
20 秒后刷新，绿色 ✓ 就是成功；仓库里会多出 `backups/2026-11-02.json`。

**5. 不用管了**

每天北京时间 02:00 自动跑，失败会发邮件。顺便还解决了 Supabase"7 天不用会被暂停"的问题。

### 恢复

仓库 `backups/` → 找那天的文件 → **Download raw file** → 网页「我的 → 导入恢复」→ 选这个文件。

## 办法 ③：手动导出（兜底，永远有效）

**我的 → 备份恢复 → 导出**，得到一个 `进销存备份_2026xxxx.json`。

它和①②的唯一区别是：**这个文件带商品图片**。图片存在每台设备自己的浏览器里（IndexedDB），体积大（一张几十 KB，几十个商品就好几 MB），云端的账本正文和历史版本都不含它。

所以关于"是不是每月要导一次"，结论是：

| 你在意什么 | 要不要每月导 |
|---|---|
| 商品、库存、单据、客户、发票、报表 | **不要**。① 已经每天自动留档 |
| 商品图片 | 看情况，见下 |

**图片其实可以不管。** 图片是"看货用"的辅助信息，丢了不影响账目、不影响对账、不影响报税。换设备或清缓存后图片没了，重新拍一张就行——而每月导出一次，换来的只是"万一哪天要"，代价是你得记着做。**记着做的那种备份，通常等于没有备份。**

真的想让图片也跟着走，有两条路：

- **手动兜底**：换手机、重装系统之前导一次（不是定期，是"要动设备之前"）
- **彻底自动化**：把图片也传到 Supabase Storage，网页自动同步。需要改一次前端代码 + 后台建一个存储桶，改完之后不用再管
